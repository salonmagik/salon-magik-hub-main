_Written by hand against the evidence above (design AD-10) — render-results.ts does not generate this section. See the implementer report for the full account of what could and could not be executed in this pass, and why._

**Coverage caveat that qualifies every statement below:** this pass ran with real `sk_test_` Paystack credentials against both the local stack (Tier B) and the dev Supabase project (Tier A), closing most of the credential-blocked gap the prior run recorded. `create-payment-session` (`PAY-BOOK-OK-*`) and the deployed webhook signature verification (`PAY-TRANSPORT-*`) now have real, passing evidence against Paystack's live test-mode API. What remains genuinely unproven, and could not be closed in this pass regardless of credentials: (1) `refund-via-paystack`'s own initiating call (`REF-a`) requires a transaction that itself came from a completed hosted-checkout charge — nothing in this harness can drive that without a human at a browser (design AD-R4); (2) the payout transfer-*initiation* calls (`W-DUP-REQ`, `W-FLOOR`, `W-OTP`) are gated on the same Tier A precondition but were never implemented against `paystack-test-client.ts` in this pass — the precondition is met (a real key is present) but no call was made, and that is recorded honestly as not-run, not assumed passing.

**(a) Payout path — go/no-go: C-3 fixed; a coverage gap remains (`W-DUP-REQ`/`W-FLOOR`/`W-OTP`), the go/no-go call on that gap alone is left to the user.**
What passed for real, now including a genuine attempt against the actual guard logic: `PAYOUT-W-OK-{GHS,NGN}`, `PAYOUT-W-FAILED-{GHS,NGN}`, `PAYOUT-W-REVERSED-{GHS,NGN}`, `PAYOUT-W-DUP-EVT-{GHS,NGN}`, `PAYOUT-AUTH-NONMEMBER-{GHS,NGN}`, and — new in this pass — `PAYOUT-W-OVER-{GHS,NGN}` all pass. With a real key present, `process-salon-withdrawal` reached its own availability guard for real and correctly refused a withdrawal above what has cleared ("Only 0.00 GHS of your 200 GHS balance has cleared... is available to withdraw right now"), resolving the prior run's "could not even reach its own guard logic" gap.
What remains unevidenced: FR-18 (`W-DUP-REQ`) and FR-20 (`W-OTP`) are still **unevidenced** — both require a transfer actually initiated against Paystack, which this pass's harness does not attempt (see coverage caveat). `W-FLOOR` (also FR-19, alongside the now-passing `W-OVER`) is unevidenced for the same reason.
**C-3 is now fixed** (`PAY-BOOK-REF-b-{GHS,NGN}`, both `pass`, `before.balance=99.5 → after.balance=0`) — implemented per `docs/design/payout-refund-wallet-not-debited.design.md`: `complete_transaction_refund` no longer debits nothing on a wallet-drawing refund; the debit is now taken up front (before the irreversible external effect) by `debit_salon_wallet_for_refund`, sized to the wallet's actual net-of-fee credit rather than the gross refund amount (the original adopted fix from `ffc1740` debited gross and would have blocked every full refund at a non-zero platform fee — corrected here), and validated by `complete_transaction_refund` before it records anything. This was re-confirmed passing against the local stack in this pass; re-run once the dev-project deploy (still outstanding — see implementer report) lands to confirm against dev as the prior three confirmations did. With C-3 resolved, the payout path's only remaining open question is the `W-DUP-REQ`/`W-FLOOR`/`W-OTP` coverage gap above, which is a "never attempted" gap, not a confirmed defect — whether that alone withholds a GO is a product call for the user, not this pass's to make.

**(b) subaccount-split-cleanup unblocked: YES, on the narrow question that item asks.** Unchanged from the prior verdict. The item is scoped to deleting the superseded subaccount/split code path (`SUBACCOUNT_SPLIT_ENABLED = false`, unplugged 2026-09-06). Nothing evidenced or unevidenced in this run bears on whether that specific dead code is safe to delete — the split path was never exercised by design (every cell ran with the flag off, per design section 15), and C-3/the DUP findings are properties of the *current* (non-split) path, not the code being deleted. The dependency this backlog item names — "blocked on your verdict" — is satisfied: this is the verdict, and it does not implicate the split code.

**(c) beta launch unblocked: NO.** Confirmed, quantified defects on the charge side, plus a genuinely narrowed but still-open coverage gap:
- **Duplicate webhook delivery is still not idempotent for `BOOK`, `CPT`, or `MSG`** (`PAY-BOOK-DUP-*`, `PAY-CPT-DUP-*`, `PAY-MSG-DUP-*`, all `fail`) — unchanged from the prior run, now re-confirmed against real Paystack-originated session references. A second identical `charge.success` delivery inserts a second `transactions` row for `BOOK` and `CPT`, and a second `messaging_credit_purchases` row *plus* doubles the `communication_credits` balance for `MSG` (that branch has no idempotency key at all — the only one of the six that doesn't). The wallet-credit side of `BOOK`/`SPT`/`INV` is correctly protected by the ledger's idempotency key in every case tested; the transaction/invoice/purchase-record side generally is not. This is now the sole confirmed, load-bearing defect blocking beta.
- **C-3 (refund does not debit the wallet) is fixed** — see (a). No longer a beta blocker.
- **The initiating Paystack calls for refund and payout transfers remain unproven** — `REF-a` (real refund-via-paystack call) and `W-DUP-REQ`/`W-FLOOR`/`W-OTP` (real transfer initiation) have no passing evidence. Session creation and webhook signature verification, previously in the same unproven state, now do (`PAY-BOOK-OK-*`, `PAY-TRANSPORT-*`, all pass for real). The remaining gap is narrower than the prior run's but not closed.

This does not mean the payment path is known-broken end to end — most of it now has real, positive evidence, including the two largest surfaces from the prior verdict's caveat (checkout session creation and webhook transport). It means beta cannot be called safe while the duplicate-webhook defect stands (BOOK/CPT/MSG double-record on a retried delivery) and while the refund/transfer initiation calls remain unattempted by this harness.
