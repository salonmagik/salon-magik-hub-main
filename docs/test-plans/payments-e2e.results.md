## Verdict

_Written by hand against the evidence above (design AD-10) — render-results.ts does not generate this section. See the implementer report for the full account of what could and could not be executed in this pass, and why._

**Coverage caveat that qualifies every statement below:** every cell in this run is Tier B, and every cell that requires a real Paystack test-mode call — session creation (`create-payment-session`), the in-product refund call (`refund-via-paystack`), transfer initiation (`process-salon-withdrawal`'s `/transfer` and `/balance` calls), and every Tier A cell — could not execute at all, because no `PAYSTACK_SECRET_KEY_GH`/`PAYSTACK_SECRET_KEY_NG` test-mode credential exists anywhere in this environment. Where a cell's *effect* (webhook processing, refund bookkeeping, transfer completion) could be reached by seeding its precondition directly instead of via the blocked initiating call, it was — and is marked as such in its note — but this means no cell in this run has proven the *initiating* calls themselves (amount computation against a live Paystack charge, a live refund actually reaching Paystack, a live transfer actually reaching Paystack) are correctly wired. That is exactly the blind spot Tier B alone was always expected to have (design AD-1, "Rejected: Tier B only") — it is not closed by this run.

**(a) Payout path — go/no-go: NO-GO (insufficient evidence to call it a go).**
What passed for real: the payout *completion* path is sound — `PAYOUT-W-OK-{GHS,NGN}`, `PAYOUT-W-FAILED-{GHS,NGN}`, `PAYOUT-W-REVERSED-{GHS,NGN}`, and `PAYOUT-W-DUP-EVT-{GHS,NGN}` all pass: a `transfer.success` debits the wallet exactly once and only once, `transfer.failed`/`transfer.reversed` never touch the wallet, and a duplicate `transfer.success` delivery is a genuine no-op. The membership check (`PAYOUT-AUTH-NONMEMBER-{GHS,NGN}`) also passes.
What is unevidenced: FR-18 (duplicate-request refusal), FR-19 (`W-OVER`/`W-FLOOR`), and FR-20 (`W-OTP`) are all **unevidenced** — every one of them requires the transfer to actually be initiated against Paystack, which this run could not do. **`PAYOUT-W-OVER` in particular could not even reach its own guard logic**: `process-salon-withdrawal` resolves and checks the Paystack key before it ever reaches the balance/availability checks, so the 500 recorded for that cell is a credential blocker, not evidence the guard works or doesn't.
Separately, **C-3 is confirmed live** (`PAY-BOOK-REF-b-{GHS,NGN}`, both `fail`): `complete_transaction_refund` recorded a completed refund against a real transaction and left the salon wallet balance unchanged. A salon can withdraw money that has already been returned to a customer. Per AD-10's note for the verdict author, this does not by itself force a no-go on `subaccount-split-cleanup` (C-3 is independent of the split/subaccount code that cleanup removes) — but it is a real, now-doubly-confirmed (static read + live RPC call) payout-path defect, and "go" on the payout path cannot be said while it stands.

**(b) subaccount-split-cleanup unblocked: YES, on the narrow question that item asks.** The item is scoped to deleting the superseded subaccount/split code path (`SUBACCOUNT_SPLIT_ENABLED = false`, unplugged 2026-09-06). Nothing evidenced or unevidenced in this run bears on whether that specific dead code is safe to delete — the split path was never exercised by design (every cell ran with the flag off, per design section 15), and C-3/the DUP findings are properties of the *current* (non-split) path, not the code being deleted. The dependency this backlog item names — "blocked on your verdict" — is satisfied: this is the verdict, and it does not implicate the split code.

**(c) beta launch unblocked: NO.** Confirmed, quantified defects on the charge side:
- **Duplicate webhook delivery is not idempotent for `BOOK`, `CPT`, or `MSG`** (`PAY-BOOK-DUP-*`, `PAY-CPT-DUP-*`, `PAY-MSG-DUP-*`, all `fail`). A second identical `charge.success` delivery — which Paystack's own retry behavior can produce — inserts a second `transactions` row for `BOOK` and `CPT`, and a second `messaging_credit_purchases` row *plus* doubles the `communication_credits` balance for `MSG` (that branch has no idempotency key at all — the only one of the six that doesn't). The wallet-credit side of `BOOK`/`SPT`/`INV` is correctly protected by the ledger's idempotency key in every case tested; the transaction/invoice/purchase-record side generally is not.
- **C-3 (refund does not debit the wallet)** — see (a).
- **Every Paystack-dependent cell is unevidenced** — see the coverage caveat above. Beta cannot be called safe on a payment path where session creation, refunds, and payouts have not been proven against a real Paystack test-mode account in this run.

This does not mean the payment path is known-broken end to end — the parts that could be tested (webhook recording for `OK`/`FAIL`/`ABD-C`/`ABD-N`, most of payout completion) passed. It means this run could not produce a "go", and did produce two confirmed, named defects that should each be their own tracked item (see the implementer report's Deviations for the exact backlog items raised).
